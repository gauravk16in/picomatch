## Findings

- [BLOCKER] build_fragments materializes a corrupted `globstar` fragment — parse.js:L396 vs crates/pmx-core/src/parse/parser.rs:296-304. The Rust `format!` literal `"({capture}(?:(?!{}{}.)*?)"` expands to `(?:(?!<SA><DP>.)*?)`; the JS closure emits `(?:(?!<SA><DP>).)*?`. The `.` (the char-consumer) moved inside `(?!…)` and one `)` is missing. Byte-exact diff on all 4 (capture × dot) combos (fresh output):
  - orig dot=false cap=false: `(?:(?!(?:^|\/)\.).)*?` — rust: `(?:(?!(?:^|\/)\..)*?)`
  - orig dot=true  cap=false: `(?:(?!(?:^|\/)\.{1,2}(?:\/|$)).)*?` — rust: `(?:(?!(?:^|\/)\.{1,2}(?:\/|$).)*?)`
  The fragment is semantically destroyed (the tempered loop `(?:(?!X).)*?` becomes a quantified lookahead, never consuming input; `/(?!)*/ ` is only Annex-B-legal in JS and likely a syntax error in `regress`). It also poisons `star` in bash mode (parser.rs:309-313 clones it, parse.js:L401). Zero C0 rows emit fragments, so the corpus is blind to it; every C1+ star/globstar byte comparison would have failed downstream. Verified by evaluating the original closure (parse.js:L395-397) vs the Rust literal expansion.
- [MAJOR] `PmxError::InputTooLong.max: f64` stringified with Rust `Display`, which is not JS `Number.prototype.toString` — C0_DESIGN.md PmxError bullet ("Display reproduces JS message bytes exactly … float semantics preserved") and parse.js:L368 (`${max}`) vs crates/pmx-core/src/error.rs:20-21. Clamp/NaN semantics are right (options.rs:92-98 ✓), the *stringification* is not. Empirical (220-case differential, infra/fixtures below):
  - `maxLength: -Infinity`, len 600 — js: `Input length: 600, exceeds maximum allowed length: -Infinity` / rs: `…​ -inf`
  - `maxLength: -0`, len 600 — js: `…​: 0` / rs: `…​: -0`
  Same class: subnormals (`5e-324` → js `5e-324`, rs long decimal). Needs a JS-faithful number formatter (or a documented `js_num` Display helper) anywhere a JS `${number}` lands in bytes.
- [MAJOR] Corpus encoder `enc()` in fixtures/canon.js:21 truncates astral-containing strings: `Array.from(s, (_, i) => s.charCodeAt(i))` iterates *code points* and indexes by *code unit*, so the last (units−points) UTF-16 units are dropped. Verified against ground truth: `'a😀a'` → canon stores `[97,55357,56832]`, truth `[97,55357,56832,97]`. Corrupts corpus rows in c0_oracle.json:
  - `text.astral-index` (activates at **C1**, asserts `output`): stored `input/consumed/output/tokens[1].value` = `[97,55357]` vs truth `[97,55357,56832]` — guaranteed red on C1 activation.
  - `guard.len.astral.ok.input` corrupt too, currently masked by `assert: ['utf16Length']`.
  Fix canon.js to `Array.from({length: s.length}, …)` and regenerate (verify-c0.js passes today only because extractor and verifier share the bug; I reproduced the same bug in my own probe first — it's an easy trap).
- [MINOR] Design I-1 deviation: `Parser` has no `braces: Vec<BraceFrame>` and no materialized `len: isize` (method instead) — C0_DESIGN.md I-1 vs crates/pmx-core/src/parse/parser.rs:41-53. Harmless in C0 (C5 owns brace frames) but it is an undeclared departure from the pinned struct shape; declare it or add the field when C5 lands.

## Proposed AGENTS.md/rulebook addition

Never hand-rebuild nested JS template-literal fragment strings in `format!`s: every emitted fragment must be a compile-time literal covered by a byte-level test against the original at the chunk that *defines* it, because one misplaced `)` is invisible until the chunk that *emits* it and then poisons all downstream oracle-1 comparisons.
